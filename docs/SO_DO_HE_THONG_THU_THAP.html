One workbook in, one workbook out

Students rank clubs and sit club tests in one place, the Hall. A PC at school, the Station, turns what they did into a single Master Workbook for the kiosk. A person prepares one file and presses one button. Nobody retypes anything in between.

Register and rank, anywhere (window W1)

One page for ranking and ticking. The Hall repeats every rule on the server, so a crafted request cannot get around the page.

  • Ticks are offered only for clubs the student ranked and that have a test, so the rule “score only clubs the student listed” cannot be broken.
  • An empty session means the student is busy that day. That is valid data, as in the current CSV rules.
  • Quotas and competition levels are not shown. Showing them can change what students rank. This is a default you can flip (Decision 5).

Sit the tests on-site (window W2)

The same web page, but its test door only opens inside the school and only while a proctor has a lab session open.

  • Question and option order is shuffled per ticket and remembered, so a resumed test looks the same.
  • Students do not see scores. That matches “Show results automatically = off” in the current form settings.
  • Soft signals (tab hidden, paste) go to the audit as information. Nothing is penalised automatically.

Close, compile, audit, release

Runs on the Station when W2 ends. A person is needed in two places only: the exceptions queue and the release click.

  • The pass bar is the one the sinh-du-lieu-clb skill already uses: 0 import warnings and 0 health warnings, except health_oversubscribed_buoi, which is a fact about competition and not a data fault.
  • With Autopilot on and a green board, the release click disappears. Default is off.
  • Rehearsal data and real data cannot be confused: MANIFEST carries data_origin = REHEARSAL or REAL, and the importer should refuse REHEARSAL outside demo mode.

The Master Workbook

A proposed contract, v0. Today's importer reads the first sheet only (decision #10), so the new input system has to read by sheet name. Both long forms already exist in mau_csv/HUONG_DAN_CSV.md (3.2 and 3.4).

The four sheets the kiosk reads

SheetColumnsRule
CLBclub_id, name, capacity, reserve_capacity, reserve_group, buoi, has_testSame as file 01 today. has_test is derived: a club with at least one question. Capacity comes from the pack, never from students.
HOC_SINHstudent_id, name, class, reserve_groupOne row per roster student, including students who never claimed a ticket. student_id keeps its case-sensitive rule (decision #13).
CHON_THIstudent_id, club_id, score, attempt_idOne row per test taken, in long form, so there is no column count to guess (today it is 5 × sessions). Score on 0 to 10. Only clubs the student ticked and ranked.
NGUYEN_VONGstudent_id, buoi, rank, club_idOne row per choice. rank restarts at 1 in every session. buoi is repeated for readability and checked against the club's own session.

What the Station asks of the new input system

  • Read sheets by name, not by position.
  • Refuse data_origin = REHEARSAL unless demo mode is on.
  • Recompute the sheet hashes and compare them with MANIFEST before importing. A mismatch is a hard stop.

  11. Type capacity into file 01

Proposed: 5 touches

  1. Fill and drop the Season Pack. This includes writing the content, which no system can skip.
  2. Homeroom hands out the QR tickets.
  3. The proctor opens each lab session.
  4. Resolve the exceptions queue (often empty).
  5. Press RELEASE (skipped on Autopilot).

Touches 2 and 3 are physical presence, not computer work. Touch 5 disappears on Autopilot.

Where it can run

You allowed the free cloud, Google Workspace or Microsoft 365. The design does not depend on the choice. The Hall is ten verbs, and any host that implements them is a valid Hall. The Hall has no scheduled jobs: it compares the clock with the window times on every request. Only the Station has a timer.

The Hall's ten verbs

My pick A for the Hall, with the Station as the only smart part. It is the only option that gets the on-site door and the test-day burst right, and it keeps names off third-party servers. B is the fallback if the school will not accept a non-school host: the ranking window, spread over days, suits Apps Script well, but lab sessions need queue-and-retry and a room code without the network check. C keeps the same structural limits as today's Forms flow, so I would not spend effort there.

Does it fit a free tier?

A rough sizing, not a measurement. With one row per saved ranking, per test start and per submit, and autosave coalesced to every 30 seconds, a student writes roughly 30 to 60 rows over the season. At 1,000 students that is 30,000 to 60,000 rows, under D1's 100,000 rows written per day even if everything happens on one day. Index writes count too, so the margin is thin. I have load-tested nothing. The dress rehearsal exists to measure real writes per ghost student, and it fails the board if projected use passes half the daily cap.

Supabase's free plan is left off the shortlist: third-party summaries report that it pauses a project after 7 idle days, which is a trap for a system used a few days per term. Firebase would also work for A, but I did not check its free-tier numbers.
